Cache coherence controllers, synthesized from three specs

Describe the protocol, the topology and the policy separately. Synapse combines them into complete controllers, checks them for deadlocks and memory-consistency violations, and emits SLICC that runs in gem5.

Every Synapse controller is named after the specs it was built from. Change one spec and you get a different controller, with nothing rewritten by hand.

Why

Every new architecture needs new coherence controllers: a second socket, an accelerator, a CXL memory pool. Today each one is written by hand, as a state machine full of transient states, and then debugged and verified on its own. The protocol, the place in the hierarchy and the cache policy are tangled together in the same code, so changing one of them means starting over.

Synapse keeps the three apart. You write them once, and recombine them for every new design.

How it works

Every coherence controller, whatever its protocol and wherever it sits, reduces to three state machines. The protocol spec provides the client and the manager, the policy spec provides the policy, and the topology spec only says where each controller sits: who is its parent, who are its children.

Client

Asks its parent for data and permissions, like a cache.

Manager

Tracks what its children hold, like a directory.

Policy

Decides when to allocate, update or replace a block.

The three machines speak different languages, and at a bridge the child may speak MESI while the parent speaks CXL. Synapse labels every state and request, in any protocol, with one tuple, ⟨Permission, Data, Coherence⟩, then fuses the transitions whose labels match. The result is one concrete controller, transient states included.

The compiler

  1. Specs

    Written in the Synapse DSL.

    protocoltopologypolicy

  2. Synthesis

    Builds every controller in the topology, then checks deadlock freedom with Murφ and memory consistency with litmus tests.

  3. Code generation

    Emits SLICC controllers and the gem5 simulation setup.

  4. gem5

    Run and measure the design like any hand-written protocol.

Try it

The artifact reproduces every experiment in the paper. The quickest path is the prebuilt Docker image; the functional test finishes in under a minute.

git clone https://github.com/TUM-DSE/Synapse
cd Synapse
docker pull carpeniem/synapse-artifact-s1_2_3:prebuilt
just shell-s1_2_3-prebuilt

# inside the container
./S1_2_3_experiments/scripts/run-functional.sh

Any x86-64 machine with Docker. Plan for about 12 GB of RAM per concurrent simulation. just is optional: every shortcut maps to a script in the repository.

S4 has its own image: carpeniem/synapse-artifact-s4.
